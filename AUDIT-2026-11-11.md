## 1. Executive summary

**Verdict: a genuinely well-engineered asset pipeline, wrapped in an under-verified product.**

The parts that matter most are better than the repository's public presentation suggests: the parser/IR/converter split is deliberate and correct, there is a real bounds-safety primitive with a documented rationale, the VFS unifies six unrelated archive formats behind one mount API, and the commit log reads like an engineer keeping notes rather than a changelog generator. This is not a half-finished tutorial project. It is a working GoldSrc/Source asset reader with a playable GoldSrc lab on top.

The problems are equally clear and they are concentrated in three places:

1. **Nothing that a user installs contains the work described in `CHANGELOG.md`.** The last release (v2.1.0, 2026-08-01) still ships `demo/sandbox/`; `main` has `demo/lab/`. 49 commits and 22,725 inserted lines are unreleased. The release zip is 710 KB and has 13 downloads. Anyone following the README gets the old thing.
2. **The test suite cannot fail.** All 21 GDScript harnesses call `get_tree().quit()` with no exit code, so every one of them exits 0 whether it verified anything or not. The 6 C++ suites do exit non-zero — but they cover 6 of roughly 60 translation units, and the single largest file in the project (the 1,020-line VFS) has no dedicated test at all.
3. **The headline GoldSrc gap is lightmaps.** Lump 8 is never read. `BSPFace` even carries `styles[4]` and `lightmap_offset` and nothing consumes them. Every level is lit by a sun found in the panorama plus ambient — an impressive stopgap that does not fix a single interior. This is the difference between "a map opens" and "a map looks like the game".

| Area | Grade | One-line reason |
|---|---|---|
| Architecture | **A−** | IR boundary is real; parsers are engine-agnostic and testable headlessly |
| Bounds safety / hostile input | **B+** | `range_fits` + `std::span` + `std::expected`; some raw `reinterpret_cast` remains |
| GoldSrc coverage | **B−** | Geometry, entities, MDL, animations and audio work; no lightmaps, no sprites, no skins |
| Source 1 / Source 2 / Enfusion | **C** | Present and partly verified; uneven, and several converters are placeholders |
| Test discipline | **D+** | Great intent, no enforcement: GDScript suites always exit 0 |
| CI | **C+** | Real Windows pipeline, but pinned to Godot 4.3 while the project targets 4.7 |
| Build system | **C** | Dual build trees are a documented landmine; no presets; warnings disabled |
| Documentation accuracy | **C−** | README still points at `demo/sandbox/`, which does not exist |
| Release hygiene | **D** | `main` is 22.7k lines ahead of the only installable artifact |
| Legal / licensing | **C** | 70 MB of Valve-derived skyboxes in git against a README that says nothing is redistributed |

## 2. What the project actually is

A Godot 4 GDExtension (C++23) that mounts a retail game installation and turns its assets into Godot resources, plus a GDScript editor dock and a playable GoldSrc scene.

```
src/
  api/          Godot-facing nodes: VFSManager, UnifiedAssetImporter, AsyncAssetImporter,
                MapPreviewViewport, TaskProgressTracker, VFSDropHandler
  core/         io (bounds-safe reader), vfs (mount/index/fallback), ir (engine-agnostic
                mesh/skeleton/animation/collision), image (DXT), math, config, logging
  parsers/      goldsrc (BSP30, WAD3, MDL10, SPR), source1 (BSP, VPK, VTF, VMT, MDL, PAA),
                source2 (VPK2), rv_enfusion (PBO, P3D, PAA)
  converters/   IR -> Godot: mesh, skeleton, material, texture, terrain, collision, sounds
  cli/          a main() that is deliberately excluded from the shared library
demo/
  addons/quebratsk_editor/   editor dock, sky loader, presets, catalogues
  lab/                       playable GoldSrc level (formerly demo/sandbox/)
  tests/                     21 GDScript verification scenes
  presets/counter_strike_1_6/ per-model animation/weapon manifests generated by tools/
tests/                       6 C++ suites, wired into CTest
```

The layering is the strongest decision in the repository, and it is stated explicitly in `tests/mdl10_parser_test.cpp`: the parser touches no `Object`, no `String`, no `Variant`, so a synthetic `.mdl` can be built in memory and decoded without a running engine. That is what makes headless testing possible at all, and `byte_reader.h` documents *why* its bounds check is written with subtraction and division:

> The obvious form, `offset + count * elem_size <= total`, wraps around `size_t` for values taken from an untrusted file and then reports success — which is exactly how several of the out-of-bounds reads in this codebase's audit came about.

That comment is the signature of someone who got burned and learned. It is the right thing to have learned, and it is applied consistently enough to matter.

### 4.2 GoldSrc gaps, ranked by leverage

1. **Lightmaps are not read.** `bsp30_parser.cpp` calls `get_lump()` for 0, 1, 2, 3, 6, 7, 9, 12, 13, 14 — never 8. `BSPFace::styles[4]` and `BSPFace::lightmap_offset` are parsed into the struct and then ignored. Consequence: no baked lighting, ever. The panorama-sun + ambient substitute is clever and looks good in screenshots of exteriors, but every corridor, doorway and indoor room is wrong. **This is the highest-value single feature in the project.**
2. **`.spr` is dead code.** `src/parsers/goldsrc/spr_parser.cpp` exists, compiles (the build globs `src/*.cpp`), and is referenced by nothing outside its own translation unit. `CHANGELOG.md` states it plainly: blood falls back to a red quad, and 76 sprite entities on `de_aztec` alone cannot exist.
3. **Animated textures are not handled.** GoldSrc encodes animation frames and alternates in the miptex name suffix (`+0`, `+A`, `+B`, …) at 10 fps per the SDK. Water, lava, slime, teleport and monitor surfaces are static today. This is cheap to add and disproportionately visible.
4. **Skin families past index 0 are not built.** Four `cs_siege` hostages declare `skin 1` and wear the wrong clothes.
5. **No visibility/leaf culling.** Lumps 4/5/10 (nodes, leaves, leaf faces) are unread, so the whole BSP draws every frame. On a 25-map game this will hurt on the larger maps before it hurts on `cs_siege`.
6. **No hitboxes.** The MDL hitbox table is not exposed, which blocks any real combat model.
7. **`func_breakable` shells, doors and ladders are scripted in GDScript, not in the importer.** Fine for a lab; not reusable by anyone consuming the extension as a library.

## 5. Code quality findings

### P0 — correctness and product

**P0-1. No lightmaps (see §4.2).** Not a bug, a missing subsystem, but it dominates the visual result.

**P0-2. GDScript tests cannot fail.**
Every harness ends with `get_tree().quit()`; Godot's default exit code is `0`. `verify_dock.gd` prints 70 lines and exits 0 no matter what it found. The most damning example is the suite written to catch the exact bug v2.1.0 was released to fix — `verify_goldsrc_anim.gd:79-81`:

```gdscript
if animated > 0 and animating == 0:
    print("  ** every model still stands still **")
get_tree().quit()
```

If animations regress to the bind pose tomorrow, that test prints a warning and exits **successfully**. A CI job could not distinguish a pass from a total mount failure. Fix is mechanical: track a failure count and call `quit(1)`.

**P0-3. The installable artifact is 49 commits behind `main`, and the README describes a directory that no longer exists.**
`README.md:226` — "### Try the sandbox", `README.md:228` — "a playable scene at `demo/sandbox/`". At `HEAD` there is no `demo/sandbox/`. `README.md:284` also references "the sandbox's movement". A new user follows the tutorial, finds nothing, and concludes the project is broken.

**P0-4. 70 MB of Valve-derived imagery is committed while the README says it redistributes nothing.**
`README.md:297`: "Quebratsk reads what you already own and redistributes nothing." `CREDITS.md:147`: "Their content belongs to Valve and none of it is redistributed here." Yet the repository tracks:

```
24,305,509  demo/assets/skyboxes/cs_siege/cs_siege_panorama_8k.png
17,892,569  demo/assets/skyboxes/de_aztec/de_aztec_panorama_flash_8k.png
15,324,981  demo/assets/skyboxes/de_aztec/de_aztec_panorama_8k.png
 6,776,513  demo/assets/skyboxes/de_aztec/de_aztec_panorama_4k.png
 1,281,577  demo/assets/skyboxes/de_aztec/de_aztec_dn.png
 ... plus ft/bk/lf/rt/up
```

The six `de_aztec_{up,dn,ft,bk,lf,rt}.png` files use GoldSrc's own skybox face naming, which is what an extraction produces. The 8K panoramas are renders built from them. Whether the author considers these "generated, therefore mine", the provenance is Valve's artwork and the README's claim is at minimum misleading. **Recommendation:** move them behind a runtime generator (the game already ships the TGAs), or Git LFS with an explicit provenance note, or drop them from the repo entirely. This is also 68% of the tracked byte count and the reason a clone pulls a 94 MB pack.

### P1 — engineering

**P1-1. Test coverage is lopsided relative to risk.**
6 C++ suites / 12,193 LOC:

| Suite | Covers | Verdict |
|---|---|---|
| `byte_reader_test` | bounds primitive | good |
| `dxt_decoder_test` | DXT1/3/5 | good |
| `anim_decoder_test` | Source 1 RLE tracks | good |
| `mdl10_parser_test` | GoldSrc mesh/skeleton/palette | good and unusually thorough |
| `paa_parser_test` | Enfusion PAA | good |
| `source_mdl_test` | Source 1 MDL | good |

Missing entirely: `vfs_manager.cpp` (1,020 lines — the layer every single import goes through), `bsp30_parser.cpp` (362), `wad3_parser.cpp`, `vtf_parser.cpp`, `vmt_parser.cpp`, `vpk2_parser.cpp`, `pbo_parser.cpp`, `game_manifest.cpp`, `texture_cache.cpp`. The VFS is the highest-ROI next test: it can be exercised with a temp directory and a synthetic WAD, no retail assets required.

**P1-2. CI tests Godot 4.3 while the project declares 4.7.**
`.github/workflows/build.yml:56` downloads `4.3-stable`. `demo/project.godot` declares `config/features = ["4.7", ...]`. The manifest itself acknowledges the gap (`quebratsk.gdextension` comments: "Godot 4.7 resolves it through a compatibility fallback, which is why this only ever failed off this developer's machine"). Net effect: CI proves the extension loads on 4.3 and proves nothing about the version users actually run. Pick one: move CI to 4.7.2, or lower the project to 4.3 and test what you ship.

**P1-3. The demo test suite is hardcoded to one machine.**
Absolute paths in tracked files:

```
demo/crossover.gd:9-11,15,19-20   C:/Program Files (x86)/Steam/...
demo/tests/build_presets.gd:19    C:/Program Files (x86)/Steam/.../cstrike
demo/tests/probe_cs16_sequences.gd:33
demo/tests/verify_animation.gd:10,11
demo/tests/verify_api.gd:6,7
demo/tests/verify_ambient.gd:26   C:/Users/you/Downloads/de_caminito
```

Nothing else can run these. There is a `SteamLibraryDetector` that already does the right thing and the lab uses it — the tests do not. Add a `QUEBRATSK_GAME_ROOT` environment override and route every test through the detector.

**P1-4. The lab has no manual path override.**
`lab.gd:_mount()` depends entirely on `SteamLibraryDetector.detect_installed_games()`. If Steam is installed in a non-standard location, or the registry key is broken (as it is on this machine: `SteamPath = c:/steam}`), the lab reports "Counter-Strike 1.6 is not installed" and there is no way to tell it otherwise. The detector's fallback is the literal `C:/Program Files (x86)/Steam`. Same fix as P1-3.

**P1-5. Warnings are off, and the source is not marked UTF-8.**
`build/CMakeCache.txt`: `CMAKE_CXX_FLAGS = /DWIN32 /D_WINDOWS /EHsc`. No `/W4`, no `/permissive-`, no `/utf-8`. 39 C++ files contain non-ASCII bytes (comments and string literals). MSVC without `/utf-8` interprets source in the system codepage; this is exactly why the project's own console output renders as `�?"` in a PowerShell capture and why `docs/TUTORIAL.md` shows `Project ��' Project Settings`. `/utf-8` is one line and removes a whole class of latent mojibake.

**P1-6. Dual build trees are a documented footgun, not a solved problem.**
`CMakeLists.txt:8-25` explains at length why Debug and Release cannot share a tree with the VS generator (godot-cpp 4.3 bakes `/MDd` at configure time). The explanation is correct. The mitigation — "configure each tree up front, do not build both from one" — relies on every future contributor reading 18 lines of comment. `CMakePresets.json` with `debug`/`release` presets and separate binary dirs is the standard fix and costs an hour.

**P1-7. `demo/project.godot` autoloads a file that is gitignored.**
```
[autoload]
McpInteractionServer="*res://mcp_interaction_server.gd"
```
`.gitignore:71` excludes `demo/mcp_interaction_server.gd`. Every fresh clone therefore logs a failed autoload on every launch. Either commit a no-op stub or remove the autoload.

**P1-8. Placeholder converters remain, against the project's own golden rule.**
`CONTRIBUTING.md` opens with "A format is NEVER documented or claimed as supported until it has been executed and verified", and names stub classes as the sin the rule exists to prevent. Yet:

| File | Lines | External refs | State |
|---|---|---|---|
| `converters/vhacd_decomposer.cpp` | 36 | 0 | Self-documented as "NOT V-HACD"; merges all vertices into one hull |
| `converters/lod_generator.cpp` | 31 | 0 | placeholder |
| `converters/pbr_autotuner.cpp` | 12 | 0 | placeholder |
| `converters/shader_bridge.cpp` | 9 | 0 | placeholder |
| `converters/lightmap_packer.cpp` | 14 | 0 | unused, and ironically the file that should hold the real lightmap work |
| `converters/async_collision_builder.cpp` | 26 | 0 | unused |

`vhacd_decomposer.cpp` is at least honest in a comment. The others are not documented as stubs anywhere a user would look. Delete them or mark them `// NOT IMPLEMENTED` at file scope.

**P1-9. `VFSManager` is 1,020 lines doing five jobs.**
Mounting, indexing six archive formats, game-slot interning, fallback search ordering, and extraction. It is well commented and not obviously wrong — the game-slot interning with a `uint16_t` and a documented overflow fallback is a nice touch — but it is the file most likely to hide a bug and the one with the least coverage. Extract the per-format indexers (`index_vpk`, WAD, PBO, GMA) behind a small interface and test them individually.

### P2 — hygiene

- **`print()`-driven observability.** 354 `print()` calls, 70 in `verify_dock.gd` alone, 20 `push_error`/`push_warning` in total. There is a `QuebratskLogger`, but the GDScript layer does not use it.
- **One `class_name` in 41 GDScript files.** Everything is `preload`ed by path, which is why scripts must know each other's locations.
- **`quebratsk_dock.gd` is 2,045 lines, 70 functions, zero signals, and `_build_ui()` is 307 lines.** The dock builds and mutates its own UI directly instead of emitting intent and letting a controller react. It is the least testable file in the project and `verify_dock.gd` (530 lines) exists mostly to compensate.
- **`CHANGELOG.md` `[Unreleased]` is 489 lines.** It mixes release notes with a design diary. Split it: keep the diary in `docs/`, keep the changelog to user-visible changes.
- **Comment/code drift.** `lab.gd:53` says "de_aztec for now: it is the only Counter-Strike map with func_breakable", while `lab.gd:55` sets `const MAP := "cs_siege"`. Eleven comments still discuss de_aztec as the active map.
- **No `.editorconfig`, no `.clang-format`, no `CMakePresets.json`, no issue/PR templates.**
- **`.atl/` is untracked** (skill-registry cache from this session's harness). Harmless, but add it to `.gitignore` or delete it.

## 6. Build system and CI

**What works.** `CMakeLists.txt` is 123 lines and mostly comments explaining real failures: the `/MDd` double-tree problem, the DLL landing in `demo/bin/Debug/` while the manifest points at `demo/bin/`, and the release build silently overwriting the debug one. The `OUTPUT_NAME` + `$<IF:$<CONFIG:Debug>,debug,release>` generator expression is correct, and `RUNTIME_OUTPUT_DIRECTORY "$<1:...>"` is the documented way to suppress the per-config subdirectory. Someone debugged this properly.

**What is fragile.**
- No presets (P1-6).
- Warnings off (P1-5).
- `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)` — convenient, but a new file only enters the build after a reconfigure; `CONFIGURE_DEPENDS` covers it at the cost of a stat sweep per build.
- `godot-cpp` pinned to `godot-4.3-stable` via FetchContent, cached in CI by hashing `CMakeLists.txt`. Changing a comment in `CMakeLists.txt` invalidates a multi-minute cache.
- CI is Windows-only. The manifest advertises Linux and macOS keys that nothing builds.

**Observed build behaviour on this machine.** The VS generator build is single-threaded in practice (one `cl.exe` at ~450 s CPU while 7 `MSBuild` nodes idled) because godot-cpp's generated bindings are one giant target. Ninja with `-j 6` is the only sane local option: 1,061 targets, of which ~1,000 are godot-cpp classes.

Steam detects games through `HKCU\Software\Valve\Steam\SteamPath` and `libraryfolders.vdf`. On this machine that key is corrupted (`c:/steam}`) and `C:\steam` does not exist, so **the lab will report "Counter-Strike 1.6 is not installed" even after CS is installed elsewhere** unless the registry is repaired or the detector is extended (P1-4).

### 7.2 Build

```powershell
# one-time, in a Developer PowerShell for VS 2022
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j 6
```

The DLL lands at `demo/bin/libquebratsk.windows.debug.x86_64.dll`, which is exactly what `demo/bin/quebratsk.gdextension` expects. A Release build needs its own tree (`build-release`) — see P1-6.

### 7.3 Unit tests (no game required)

```powershell
ctest --test-dir build --output-on-failure
```

Six suites; they exit non-zero on failure by design. This is the only part of the test surface that can gate anything.

### 7.4 GoldSrc integration tests (game required)

```powershell
godot --headless --path demo --quit-after 600 res://tests/verify_goldsrc_anim.tscn
```

Repeat for `verify_collision`, `verify_entities`, `verify_map_textures`, `verify_sounds_resolve`, `verify_ambient`, `verify_cz_maps`, `verify_weapon_manifest`, `verify_weapon_actions`, `verify_game_order`, `verify_bodygroups`, `verify_body_choice`, `verify_saved_scene`, `verify_animation`, `verify_animation_set`, `verify_api`, `verify_materials`, `verify_paa`, `verify_dock`.

**Read the output, do not trust the exit code** (P0-2). Compare against the numbers in §4.1 — they are the project's own baseline.

### 7.5 The lab (the real test)

Open `demo/project.godot` in Godot 4.7.2, let it import, then run `demo/lab/lab.tscn`.

Expected console output on a working install:
```
[lab] mounted cstrike: N container(s)
[lab] sun found in the panorama ...
```
Then: WASD + mouse, click to fire, R reload, Space jump, Ctrl crouch, Shift walk, V noclip, Escape releases the cursor.

What to look at, in order of what is most likely still wrong:

1. **Lighting.** Interiors will be uniformly lit. That is the missing lightmap, not a bug in the lab.
2. **Sprites.** Blood, muzzle flashes, explosions and 76 `de_aztec` entities will be missing or flat quads.
3. **Doors/lifts.** `cs_siege` has 126 brush entities; walk into every one.
4. **Water and ladders.** 9 water bodies, 6 ladders.
5. **Sound.** 244/253 map sounds resolved; listen for the 9 that did not.
6. **Hostages.** Four on `cs_siege`, all wearing `skin 1` clothes they should not be wearing.

### 7.6 Running with no Steam at all

Not currently possible. The VFS can mount a directory, so a manually assembled `cstrike/` tree (maps + `*.wad` + `models/` + `sound/`) would work, but every test and the lab go through `SteamLibraryDetector` first. This is the argument for `QUEBRATSK_GAME_ROOT` in one sentence.

## 8. Recommended order of work

**Before any new feature — make the project testable and shippable (1–2 days):**

1. `get_tree().quit(1)` on failure in all 21 harnesses; add a `--headless` CI job that runs them and fails the build. Without this, every later claim is unverifiable.
2. `QUEBRATSK_GAME_ROOT` override in `SteamLibraryDetector`, and route the lab + all tests through it. Removes every hardcoded `C:/...` path.
3. `/utf-8 /W4 /permissive-` and fix what surfaces.
4. `CMakePresets.json` with `debug`/`release`.
5. Fix README `demo/sandbox` → `demo/lab`, regenerate the release, tag 2.2.0. **Ship the lab.** Right now the only installable thing is a four-day-old snapshot.

**Then the GoldSrc feature work, in this order (each one is visible immediately):**

6. **Lightmaps.** Read lump 8. For each face, compute extent from the texture vectors, sample `lightmap_offset` with the +16-unit luxel grid, honour `styles[0]`, build an atlas, emit UV2, and multiply in a shader. The `lightmap_packer.cpp` file already exists and is empty — this is where it goes. Expect the single largest visual jump in the project.
7. **Wire `.spr`.** The parser exists; connect it to `env_sprite`, `env_glow`, blood and muzzle flashes. GoldSrc sprites are indexed 8-bit with a palette and an optional transparency colour, plus `SPR_ADDITIVE`/`SPR_ALPHATEST` render modes.
8. **Animated textures.** `+0`/`+A`… suffix chain, 10 fps, plus `TURBULENT`/`WAVY` miptex flags on water.
9. **Skin families.** Index the texture table by `(model, skin)`.
10. **Vis/leaf culling**, then **hitboxes**, then the gameplay that the last four commits were building toward (hostages follow, enemies path).
